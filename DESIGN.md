## 1. Introduction

### 1.1 Purpose

The SRS says *what* Selfish Launcher must do and deliberately leaves *how* and *with what* to a separate technical design (SRS §1.1, C-1). This is that design. It chooses the language, UI framework and build toolchain. It maps the three layers of SRS §7 onto modules and packages, and it justifies every third-party component. It also defines how each requirement is verified.

If this document and the SRS disagree, the SRS wins and this document is corrected.

### 1.2 Conventions

- Design decisions have IDs `TD-nn`, and each one cites the SRS IDs it serves.
- `FR-`, `UI-`, `IF-`, `NFR-`, `AR-`, `AC-`, `C-` and `Q-` IDs refer to [SRS.md](SRS.md).
- A **port** is an interface that the Domain defines for one external dependency (AR-03). An **adapter** is that port's Android implementation.
- "API 31+" means Android 12 (API level 31) or later.
- `…` in package names stands for the package root (TD-07).

## 2. Technology choices

### 2.1 Decisions

| ID | Decision | Serves |
|---|---|---|
| TD-01 | **Language: Kotlin** for all production, test and build-script code. | AR-08, NFR-MNT-01 |
| TD-02 | **UI framework: Jetpack Compose**, using only the `runtime`, `ui`, `foundation` and `animation` artifacts. No Material components. | UI-01 to UI-08, FR-GEST-*, FR-ANIM-*, NFR-PERF-07 |
| TD-03 | **Build: Gradle** with the checked-in wrapper and the Android Gradle Plugin (AGP), plus the Kotlin, Compose-compiler and kotlinx-serialization Gradle plugins. All versions live in one `gradle/libs.versions.toml`. Builds run on JDK 17. | AR-08 |
| TD-04 | **SDK levels: minSdk 29 (Android 10)**, proposed as the answer to Q-1 (§2.3). compileSdk and targetSdk are the latest stable level when the project is scaffolded (API 37), and are raised once a year. | Q-1, FR-GEN-02, FR-THM-03, FR-GEST-04 |
| TD-05 | **Release build:** R8 full mode with resource shrinking. A baseline profile is generated by the benchmark module and shipped with `profileinstaller`. | NFR-PERF-01, NFR-PERF-07 |
| TD-06 | **No proprietary SDKs:** no Google Play Services, Firebase, analytics or crash-reporting library anywhere in the dependency graph, enforced by a build check (§8.2). | NFR-PRIV-02, NFR-PRIV-07 |
| TD-07 | **Application ID and package root:** `io.github.twonet.selfish`. This is a placeholder until Q-4 (name) and Q-7 (distribution) are settled. | FR-GEN-01 |

### 2.2 Why Kotlin and Compose

- **A launcher is mostly platform integration.** That covers the Home role, `LauncherApps`, `WallpaperManager`, a `NotificationListenerService`, `JobScheduler` and accessibility. These are Java and Kotlin APIs, and Kotlin calls them directly, with no bridge or glue code.
- **Compose covers the interaction model.** The SRS needs:
  - pointer input with velocity tracking;
  - `Animatable` springs that can be caught mid-flight (FR-GEST-01 to FR-GEST-03);
  - pointer input that a page can watch before its elements, for pulley menus (FR-GEST-05);
  - semantics with custom accessibility actions (FR-GEST-09, NFR-A11Y-01, NFR-A11Y-02);
  - automatic right-to-left mirroring (NFR-L10N-03) and `sp` font scaling (NFR-A11Y-04).
- **Why no Material.** The look is translucent glass with highlight-color glows (UI-01, FR-ANIM-04), not Material surfaces and ripples. `foundation` already provides `BasicText`, `BasicTextField`, lazy grids and gesture detection. The launcher's own components are built on those, and leaving Material out helps the 10 MB budget (NFR-PERF-07).
- **The Domain is plain Kotlin on the JVM.** Its tests run with `./gradlew test`, with no device or emulator (NFR-MNT-01).

### 2.3 Why minSdk 29

| Capability | Available from | Needed by |
|---|---|---|
| `RoleManager` request for the Home role | API 29 | FR-GEN-02 |
| System-wide dark theme | API 29 | FR-THM-03. FR-THM-04 remains as a defensive branch. |
| System gesture insets (gesture navigation) | API 29 | FR-GEST-04, NFR-COMP-01 |
| `ImageDecoder` (validation, cropped decoding) | API 28 | FR-WP-04, FR-WP-14 |
| `WallpaperColors` | API 27 | FR-AMB-03 |
| `java.time` | API 26 | Domain clock and dates |
| Cross-window blur | API 31 | FR-GRID-01. Below API 31, the stronger dim of NFR-COMP-03 is used. |

Raising minSdk later is cheap. Lowering it would mean fallbacks for the first three rows. The device-share figures should be checked when Q-1 is closed.

### 2.4 Alternatives considered

| Alternative | Why not |
|---|---|
| Rust domain crate with a Kotlin UI, bridged by UniFFI and cargo-ndk (keeps the current Cargo project) | It needs two languages, two build systems and an FFI boundary for a domain layer of a few thousand lines. It also adds UniFFI, JNA and a native library per ABI (AR-08, NFR-PERF-07). In Kotlin, the Domain is already testable without a device. |
| All-Rust UI (for example Slint or egui on `android-activity`) | Every adapter becomes hand-written JNI, and services and jobs still need Java or Kotlin classes. Screen-reader support in Rust UI toolkits on Android is immature, which puts FR-GEST-09 and NFR-A11Y-* at risk, and all of those are M. |
| Kotlin with Android Views | Workable, but gesture-driven, interruptible transitions and one shared motion component (AR-04) take noticeably more code than in Compose. |
| Flutter | Every capability in SRS §5.2 needs a platform channel, and the engine alone uses a large part of the 10 MB budget (NFR-PERF-07). |

### 2.5 The existing Cargo project

`Cargo.toml`, `Cargo.lock` and `src/main.rs` were a placeholder from the repository's first commit. They were removed when the Gradle project was scaffolded (§11, issue #2).

## 3. Code structure

### 3.1 Modules

The three layers of SRS §7 map to three Gradle modules, plus one test-only module.

```
selfish-launcher/
├── SRS.md · DESIGN.md · REVIEW-CHECKLIST.md
├── settings.gradle.kts · build.gradle.kts · gradle/libs.versions.toml
├── domain/      Kotlin/JVM library    ── DOMAIN
├── adapters/    Android library       ── ADAPTERS
├── app/         Android application   ── PRESENTATION + composition root
├── systemtest/  Android test module   ── System tests in their own process (never shipped)
└── benchmark/   Android test module   ── Macrobenchmarks, baseline profile (never shipped)
```

```
┌───────────────────────────────────────────────────────────┐
│ :app                                       PRESENTATION   │
│ MainActivity · ui/… screens, motion, tokens               │
│ AppGraph (composition root, the only file that sees       │
│           :adapters)                                      │
└───────────────┬─────────────────────────────▲─────────────┘
       actions  │                             │  state (StateFlow)
┌───────────────▼─────────────────────────────┴─────────────┐
│ :domain                                    DOMAIN         │
│ LauncherStore · rules · policies · ports (interfaces)     │
└───────────────┬─────────────────────────────▲─────────────┘
      commands  │  (calls through ports)      │  data (Flows the ports define)
┌───────────────▼─────────────────────────────┴─────────────┐
│ :adapters                                  ADAPTERS       │
│ one class per port: apps · storage · wallpaper · bing ·   │
│ scheduler · os · notifications* · usage*   (* optional)   │
└───────────────────────────────────────────────────────────┘
```

**How this satisfies AR-01.** At runtime, calls flow downward exactly as in SRS §7: Presentation → Domain → Adapters. At compile time the Domain *owns* the port interfaces, and `:adapters` implements them (dependency inversion). As a result, `:domain` depends on no Android code and can be tested with fakes (AR-03). No layer calls upward: adapters report changes only by emitting on the `Flow`s their port declares, which is the "data" arrow in SRS §7.

| Module | Type | May depend on | Must not depend on |
|---|---|---|---|
| `:domain` | Kotlin/JVM library | kotlinx-coroutines-core, kotlinx-serialization-json | Android SDK, `:adapters`, `:app` |
| `:adapters` | Android library | `:domain` | `:app`, Compose |
| `:app` | Android application | `:domain`. `:adapters` only from `AppGraph.kt`. | — |
| `:systemtest` | Android test module, self-instrumenting | `:app` (as the target) | — (not shipped) |
| `:benchmark` | Android test module | `:app` (as the target) | — (not shipped) |

**Enforcement**

- `:domain` uses the `kotlin("jvm")` plugin, so `android.*` is not on its classpath. The compiler rejects any Android import.
- `:adapters` does not apply the Compose plugin and cannot depend on `:app`, because Gradle rejects the cycle.
- `LayerRulesTest`, a JVM test in `:app`, scans `app/src/main` and fails in two cases:
  - any file other than `AppGraph.kt` imports `….adapters`;
  - anything under `ui/` imports an OS-service or network package, such as `android.app.WallpaperManager`, `android.content.pm`, `android.net`, `java.net`, `android.app.job`, `android.provider.Settings`, `android.service.notification` or `android.app.usage`.
- Window-level APIs that are part of the UI toolkit stay in Presentation, because they *are* the UI framework, not the OS services that AR-01 means. That includes view haptics, insets, system-bar appearance, window blur and accessibility semantics.

### 3.3 State and data flow (AR-02)

- **One store.** `LauncherStore` (in `:domain`) owns one `MutableStateFlow<LauncherState>`. It exposes `state: StateFlow<LauncherState>` and `dispatch(action: Action)`.
- **One state.** `LauncherState` is an immutable data class containing:
  - the layout (grid items and Home covers), the app catalog and the settings;
  - the resolved appearance and the ambience (current wallpaper entry and highlight color);
  - the open layer with its overlays, and the search query;
  - the pending remorse action;
  - the current notifications (when enabled);
  - the wallpaper status: last successful update, and any wallpaper waiting to be applied;
  - the time for Home's clock.
- **Pure reducer plus effects.** `reduce(state, action)` returns the new state and a list of `Effect`s, and is a pure function. An effect runner carries out the effects through the ports in the store's coroutine scope and dispatches the results back as actions. Reducer tests need no fakes; effect tests use the port fakes.
- **Presentation renders state and sends actions.** It collects `state` with `collectAsStateWithLifecycle()` and keeps only transient UI state: drag progress while a gesture is in flight, scroll positions, cursor position and running animations. When a drag settles, it dispatches, for example, `Action.LayerSettled(Layer.AppGrid)`. When the Domain changes the layer (for example on a Home press), Presentation animates toward the new target.
- **Ports push changes as `Flow`s**: catalog changes, the system dark theme, the animator scale, notifications and access revocations. The store collects them and turns them into actions.
  - The clock (`OsSettings.clock`) is collected only between `HomeShown` and `HomeHidden`, so its time-tick receiver is registered only while the launcher is on screen (FR-HOME-02, NFR-PWR-02).
  - So is notification access (`NotificationSource.granted`), which the system announces with no broadcast. Collecting it again on every `HomeShown` checks it again, for example on the return from the system's access screen. The notifications themselves are collected only while the launcher is on screen and they are on (§5.5). *Built in #10.*
- **Two queries: icons and wallpaper images.** Icons are pixels to draw, not launcher state, and 300 of them would not fit in state comfortably (NFR-PERF-05). So the store also offers `icon(app, sizePx)`, which asks the `AppCatalog` port and returns plain ARGB pixels (`AppIconImage`). Presentation turns them into bitmaps and caches them (§5.1). The state carries each app's `version`, so an updated app's icon is loaded again (FR-GEN-06).
  - `wallpaperImage(id)` returns a cached wallpaper image's bytes from `LocalStorage`. Presentation's `WallpaperImages` decodes them off the main thread, at the smallest power-of-two sample that covers the Events card's thumbnail (FR-EVT-03). *Built in #10.*
- **Persistence.** After each layout or settings change, the store writes the affected document through `LocalStorage`. Writes run on a background dispatcher, consecutive writes are merged, and every write is atomic (§5.3).
  - **Restore first.** `start()` subscribes to the ports at once, because a scheduled run emitted before anyone listens is lost. It holds their events back until `Action.Restored(layout, settings)` has been dispatched, so every feature sees the saved state. `LauncherState.restored` is false until then, and Home shows only the wallpaper (FR-GEN-08).
  - **No saved layout is a first run.** `LauncherState.layout` stays `null` when nothing usable was saved, until the first-run layout is built (§4.2).
  - **Savers** compare each new value with the last one written. Nothing is written at start, and a change made before a saver starts is not lost. A document whose read *failed* (as opposed to one that was missing or corrupt) is not written again in that process, so a passing storage error can't replace the user's file with defaults.

**Threading**

- The store and reducer run on the main thread. Reducers are small and pure, and search over 300 apps is well under a millisecond.
- Adapters are main-safe: each one moves its own blocking work (I/O, decoding, `PackageManager` calls) to `Dispatchers.IO` or `Dispatchers.Default`.
- Wallpaper download, decoding and application never touch the main thread (NFR-PERF-06).

### 3.4 Composition root

- `SelfishApp` (the `Application`) creates one `AppGraph`. It constructs every adapter, then a `LauncherStore` with a process-wide `CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)`.
- That one store is used by `MainActivity` and `WallpaperJobService`. Wiring is plain constructor injection, with no DI framework (§7).
- The store lives as long as the process, so a remorse timer still fires after the user leaves for another app (FR-GEST-06), and the store survives Activity recreation.
- After the process is killed, `AppGraph` rebuilds the state from storage and opens on Home with the saved layout (FR-GEN-08). Navigation state is deliberately not restored.

## 4. Domain layer

Every component here is plain Kotlin, has no Android imports, and is covered by JVM unit tests (NFR-MNT-01). Time comes from an injected `java.time.Clock`, and timers use injected coroutine dispatchers. That lets tests use virtual time.

### 4.1 Launcher state and navigation

```
Layer:    Home | AppGrid | Events | TopMenu | Settings(page) | WallpaperDetails | Tutorial(step)
Overlays: Folder(id) · ContextMenu(target)     (stacked over a layer)
```

| Rule | Serves |
|---|---|
| `LauncherState` holds one `layer` and a stack of `overlays` (topmost last). Feature issues add the layers and overlays they build; the rules below don't change. | SRS §3.2 |
| `Action.Back` pops the topmost overlay first, then the layer, and stops at Home. On bare Home it changes nothing: the reducer returns the same state. | FR-GEN-04, SRS §3.2 |
| `Action.HomePressed` closes every overlay and layer. On bare Home it changes nothing. | FR-GEN-03 |
| `Action.Launch(app, bounds)` closes any context menu, and is ignored while another launch is in progress. In-progress means until the launcher stops (`Action.HomeHidden`) or 1 s has passed. Each launch is numbered and starts an `Effect.DispatchAfter(1 s, LaunchTimedOut(n))`; a timeout whose number isn't the current launch's is ignored, so a stale timer can't end a newer launch early. | FR-GEN-05 |
| `Effect.DispatchAfter(delay, action)` dispatches an action later in the store's scope, so it fires after the user leaves the launcher. It runs in virtual time in tests. The remorse queue (§4.6) uses it too. | FR-GEN-05, FR-GEST-06 |
| `LauncherState.firstRun` is true when nothing usable was saved at start. On a first run, once the state is restored *and* the launcher is on screen (`Action.HomeShown`), the reducer emits `Effect.OfferDefaultHome` once per process. The store shows the system prompt only if the launcher isn't the default already. Waiting for the screen matters because the process may have started for the background job, with no Activity to show the prompt over. | FR-GEN-02, FR-ONB-01 |
| A catalog change reconciles the saved layout (`CatalogReconciler`, §4.2), and closes a context menu whose app is gone. | FR-GEN-06 |

The store asks `AppCatalog.defaultApps()`, falling back to none if that fails, and dispatches `DefaultAppsResolved`, which builds `LayoutRules.firstRun` while there is still no layout. The savers then write it. A layout that couldn't be *read* also gets a first-run layout, but it is never saved over the unread file (§3.3). | FR-HOME-07, FR-ONB-01 |

Folders have no context menu: a long-press only lifts them, and their actions live in their panel's pulley menu. Opening one replaces any other. Back, Home, a tap outside (`CloseContextMenu`), a drag, a launch, choosing an item and moving to another layer close it. | FR-HOME-05, FR-HOME-06, FR-GRID-06 |
| `AddToHome`, `RemoveFromHome`, `MoveCover`, `MoveGridItem` and `DropOnto` apply the `LayoutRules` operations and close the menu. `AddToHome` on a full Home changes nothing: the menu already says Home is full. | FR-HOME-05, FR-HOME-06, FR-GRID-05, FR-GRID-08 |
| `OpenFolder(id)` pushes `Overlay.Folder(id)`, closing any menu, only on the App Grid, for a folder that exists and isn't waiting to be removed; one folder is open at a time. `CloseFolder` (a tap on the dim) pops it with anything over it; Back and Home close it as they close any overlay. | FR-FOLD-03 |
| `AddToFolder`, `MoveInFolder` and `RenameFolder` apply their `LayoutRules` operations. `TakeOutOfFolder(app, to)` also closes the folder: the app was dragged past the panel's edge, and the drag carries on in the grid (§6.4). A layout change or catalog change that removes the open folder, such as a drag-out or an uninstall that dissolves it, closes its overlay and anything over it (`pruneOverlays`). | FR-FOLD-04, FR-FOLD-05, FR-FOLD-06 |
| `RemoveFolder(id)` closes the folder and starts a remorse timer (§4.6); the folder stays, faded and closed to drops and taps, until `RemorseDue(n)` removes it. `CancelRemorse` (a tap on the banner) keeps it. | FR-FOLD-07, FR-GEST-06 |
| `OpenAppInfo` and `Uninstall` close the menu and emit `Effect.OpenAppInfo` and `Effect.RequestUninstall`, which the store passes to `AppCatalog`. An uninstall the user confirms arrives later as a catalog change. The menu offers Uninstall only for apps that aren't system apps (`AppEntry.removable`, §5.1). | FR-GRID-06, FR-GRID-09 |
| `Action.LayerSettled(layer)` is where a released swipe, or the screen reader's "Show apps", ends up (§6.3). On the current layer it changes nothing; otherwise it moves there and closes the overlays, which belong to the layer they were opened on. Hiding the launcher leaves the App Grid open, so Back from an app launched from it returns there; a Home press closes it. | FR-GRID-01, FR-GRID-04, FR-GEN-03 |
| `Search(query)` sets `LauncherState.query`, only on the App Grid, and closes any context menu, because the results replace the grid's items. The grid shows results while the query has something besides spaces in it (`searching`). *Built in #9.* | FR-SRCH-01 |
| Closing the App Grid clears the search query and hides the keyboard. The reducer keeps the query empty whenever the layer isn't the App Grid, whichever action left it. Hiding the launcher keeps it, so Back from an app launched from the results returns to them. The keyboard is not an overlay: the system's input method takes Back to hide itself before the launcher sees it, so the keyboard stays with the search field as transient UI state (§6.4), as it does for a folder name being edited. | FR-SRCH-05 |
| `Layer.Events` is reached like the App Grid, by `LayerSettled` from a released sideways swipe or the screen reader's "Show events", and Back and Home close it by the rules above. *Built in #10.* | FR-EVT-01, FR-GEN-03, FR-GEN-04 |
| `LauncherState.wallpaper` is the image of the day in use, a `WallpaperEntry` with its image, title, copyright text and link; #14 fills it in. `OpenWallpaperDetails` moves to `Layer.WallpaperDetails`, which #14 draws, only while there is an entry, so neither the Events card nor its menu item appear before then. `OpenLink(url)` emits `Effect.OpenScreen(Link)`. *Built in #10.* | FR-EVT-03, FR-EVT-06, FR-WP-10 |
| Notifications are on (`notificationsOn`) while "Notifications in Events" is on *and* access is granted (`notificationAccess`, `null` until first checked). `TurnOnNotifications` turns the setting on only with access granted; without it, it sets `awaitingNotificationAccess` and emits `Effect.RequestNotificationAccess`, and access granted while waiting turns the setting on. After every action, access known to be missing turns the setting off (a revocation, even one made while the process was dead), and with notifications off the list, the dismissals waiting for confirmation and any pending clear are dropped. The setting is never on while access is known to be missing, so these rules can't undo "Turn on". `HideNotificationsCard` sets `Settings.notificationsCardDismissed`, saved with the settings. *Built in #10.* | FR-EVT-04, FR-EVT-07, FR-ONB-04, NFR-PRIV-05 |
| `NotificationsChanged(items)` replaces the list while notifications are on. `DismissNotification(key)` removes a dismissible one at once, records its `NotificationRef` (key and post time) in `dismissing` until the system reports it gone, and emits `Effect.DismissNotifications`; one updated meanwhile has a new post time, and shows. `OpenNotification(key, bounds)` is a launch, under the launch guard. `ClearNotifications` starts a remorse timer for the refs of the dismissible notifications shown at that moment, so one that arrives during the countdown isn't cleared. *Built in #10.* | FR-EVT-04, FR-EVT-05, FR-EVT-06, FR-GEN-05 |
| `Settings` holds every setting from SRS §4.13, with the SRS defaults (for example Appearance = System, Daily Bing wallpaper = On). | FR-SET-01 to FR-SET-17, FR-THM-02 |

### 4.2 Layout rules

Layout operations are pure functions in `LayoutRules` over `Layout(grid: List<GridItem>, home: List<AppId>)`, where `GridItem = App(AppId) | Folder(id: FolderId, name, apps: List<AppId>)`. The schema version lives in the saved document, not in the model (§4.7).

- **App identity.** `AppId` is (package, launch activity, user serial number). It is stable across reboots and app updates (SRS §8).
- **Folder limits are types.** Home is a list of `AppId`, and a folder holds only `AppId`s. So a folder cannot be nested or placed on Home (FR-FOLD-08).
- **Folder IDs.** `nextFolderId` returns one more than the largest ID in use.
- **Saved layouts are normalized.** `normalize(layout)` restores the invariants that don't depend on the catalog: each app once (the first wins), no empty or one-app folders, unique folder IDs, and at most 9 distinct covers. It runs on every layout read from storage (NFR-REL-03).

| Operation | Rule | Serves |
|---|---|---|
| `addToHome`, `removeFromHome` | At most 9 covers. Adding a tenth returns `HomeFull`. | FR-HOME-05 |
| `moveCover`, `moveItem` | Moves the item and keeps the order of everything else. `moveItem` finds apps by `AppId` and folders by `FolderId`, so a folder renamed during a drag is still found. | FR-HOME-06, FR-GRID-05, FR-GRID-07 |
| `coverColumns(n)` | 1 to 4 covers → 2 columns; 5 to 9 → 3 columns. | FR-HOME-03 |
| `dropOnto(app, target)` | Creates a `Folder("Folder", [target, app])` at the target's position. Only for two different apps that are each on their own in the grid. Home is unchanged: an app in a folder can still be a cover. | FR-GRID-08, FR-FOLD-01 |
| `addToFolder(app, folder)` | Moves an app that is on its own in the grid to the end of the folder; its slot closes up. An app already in a folder, or a missing folder, changes nothing. | FR-FOLD-05, FR-FOLD-08 |
| `removeFromFolder(app, to)` | Takes the app out of its folder and puts it on its own at `to` in the resulting grid, clamped. A folder left with one app dissolves into that app, in the folder's place. | FR-FOLD-05, FR-FOLD-06, AC-08 |
| `moveInFolder(app, to)` | Moves an app within its folder; the others keep their order. | FR-FOLD-05 |
| `renameFolder(folder, name)` | Trims the name; a blank name keeps the old one. | FR-FOLD-04 |
| `removeFolder(folder)` | Puts the folder's apps back into the grid in its place, in their order. | FR-FOLD-07 |
| `sortAlphabetically` | Uses a `java.text.Collator` for the device locale. | FR-SET-10 |
| `firstRun(apps, defaults)` | Builds the grid in the order of `apps`, which the store keeps alphabetical. Home gets the default phone, messaging, browser and camera apps, in that order, each once and only if it is in `apps`. | FR-HOME-07, FR-ONB-01, FR-SET-16 |

### 4.3 Wallpaper policy

`WallpaperPolicy` is a set of pure decisions. Its inputs are the settings, the wallpaper index (cached entries, current and pinned image, last check, last success, failures today), the time, the network state and whether a gesture is in progress.

| Decision | Rule | Serves |
|---|---|---|
| When to check | **Home shown:** check if the last check is more than 3 h old. **Background job:** every run, on a 3 h period (§5.4). **Never** when Daily Bing wallpaper is off. | FR-WP-02, FR-WP-13 |
| Gates | Skip while Data Saver or Battery Saver is on. Skip on a metered network when "Wi-Fi only" is set. | FR-WP-06 |
| Daily cap | At most 8 checks per day, retries included. | NFR-PWR-01 |
| Retries | After a failure, retry after 15 min, then 1 h, then 4 h. At most 3 retries a day; the count resets on success. No error UI. | FR-WP-11 |
| What to download | The newest feed entry whose identity is not already cached. Identity is the hash, or the start date plus market. On first run and after gaps, request 8 entries. | FR-WP-02, IF-WP-01, IF-WP-04 |
| Which size | The portrait `{urlbase}_1080x1920.jpg`, falling back to the landscape image. `Crop.center(image, screen)` returns the centered rectangle with the screen's aspect ratio. Images are never scaled non-uniformly. | FR-WP-04 |
| What to apply | The newest cached image, unless an image is pinned. Pinned means new images are still cached but not applied. | FR-WP-01, FR-WP-08, FR-TOP-03 |
| When to apply | Immediately in the background. While Home is visible, after the current gesture ends, with a crossfade (§6.6). | FR-ANIM-10 |
| Until the first image | The system wallpaper is left untouched. | FR-WP-12 |
| Cache eviction | Keep the 8 newest images plus the pinned and the applied one. Then evict the oldest unpinned images until the cache is under 25 MB. | FR-WP-07, NFR-PWR-04, NFR-REL-02 |
| Turning Daily off | Cancel the job, delete the cache and leave the system wallpaper as it is. | FR-WP-13 |
| Market | `MarketResolver(locale)` tries an exact language-and-region match against the supported-market table, then the language's default market, then `en-US`. | FR-WP-03, Q-5 |

### 4.4 Appearance and ambience

**Appearance**

- `resolveAppearance(mode, systemDark: Boolean?)` returns Light or Dark.
- An explicit Light or Dark mode wins.
- In System mode it follows the device. If the device has no setting (`null`), it returns Light.
- Serves FR-THM-01, FR-THM-04 and FR-THM-06.

**Highlight color**

- **Derive** (FR-AMB-01). `deriveHighlight(pixels)` takes a pixel array sampled from the image (up to 128 × 128) and runs once per image, at download time:
  - pixels are bucketed by hue and lightness;
  - each bucket is scored by population × saturation², with near-gray, near-black and near-white penalized;
  - the best bucket's mean color wins;
  - below a minimum score, the default highlight token is used instead.
- **Adjust** (FR-AMB-02, NFR-A11Y-03). `adjustForContrast(color, appearance)` changes only lightness: lighter in Dark, darker in Light. It stops at a contrast of at least 3:1 against the worst-case glass for that appearance. 3:1 is enough because the highlight is used only for large text and UI components, never for body text (FR-AMB-04).
- **Store.** The derived color is saved with the wallpaper entry (SRS §8), so switching ambiences never decodes an image.
- **Wallpapers set elsewhere** (FR-AMB-03). If `SystemWallpaper.currentId()` differs from the ID recorded at the launcher's last apply, the wallpaper came from somewhere else. Then the highlight comes from `WallpaperColors`, or the default color, adjusted the same way.
- **Presets** (FR-AMB-05, C). The 8 presets go through the same adjustment.

`Contrast` implements WCAG 2.1 relative luminance and the contrast ratio. Presentation's token tests reuse it (§6.5).

### 4.5 Search ranking

*Built in #9.*

- `TextNormalizer.normalize(text)` applies NFD decomposition, drops combining marks, lowercases with `Locale.ROOT`, and makes each run of spaces one, with none at either end. The query goes through it too.
- `TextNormalizer.wordStarts(name)`: 0, and every letter or digit that follows something else, such as a space, a hyphen or an apostrophe.
- `SearchRanker(apps, collator)` normalizes the names, finds their word starts and sorts them by `Collator` once, when it is built. Presentation builds one per catalog change (`remember(state.apps)`), not per keystroke (NFR-PERF-04).
- **Rank 0:** the name, from its start or from any word start, starts with the query. So "play st" finds "Google Play Store".
- **Rank 1:** the query appears anywhere else in the name.
- No match: the app is excluded. A blank query matches nothing; the grid then shows its items.
- Ties keep the `Collator` order. The ranker is given the whole catalog, so apps inside folders are included.
- Serves FR-SRCH-02.
- `SearchRanker` is a pure function with no ports, so search cannot reach the network (FR-SRCH-06).

### 4.6 Remorse queue

- `RemorseQueue` holds at most one pending destructive action, `LauncherState.remorse`: a `Destructive` action and the number of its timer. *Built in #8 for removing a folder; #10 added clearing notifications;* #18 adds its actions.
- Starting one emits `Effect.DispatchAfter(5 s, RemorseDue(n))`. The timer fires in the store's scope, so the action runs even after the user navigates away. A `RemorseDue` whose number isn't the pending one's is stale and does nothing, as with launch timeouts.
- A second destructive action commits the pending one right away, with its effects: committing returns the next state and effects, as clearing notifications needs `Effect.DismissNotifications`.
- Nothing changes until the action is committed, so cancelling just drops it. The pending action isn't saved: if the process dies first, nothing is lost.
- The reducer keeps no clock, so the banner's countdown runs from when it appears, as transient UI state (§6.4), rather than toward a deadline held in state.
- Used for clearing notifications, removing a folder, sorting A–Z and resetting the layout.
- Serves FR-GEST-06, FR-FOLD-07, FR-EVT-06, FR-SET-10 and FR-SET-16.

### 4.7 Persistence and migration

- There are three documents. Each is a `VersionedDocument` over a `@Serializable` class, and `VersionedDocument` stamps a `schemaVersion` key into the JSON:
  - `layout.json` (`LayoutDoc`), included in backup;
  - `settings.json` (`SettingsDoc`), included in backup;
  - `wallpapers.json`, the cache index, which is not backed up (SRS §8). It arrives with #14.
- **Reading.** Parse to a `JsonObject`, then run the pure migrations `vN → vN+1` up to the current version (AR-07). Then decode leniently:
  - unknown keys are ignored;
  - invalid enum values fall back to their default;
  - invalid list items are dropped one at a time (`LenientListSerializer`);
  - missing fields take their default;
  - if decoding still fails, the saved fields are laid over the default one at a time, and each field that doesn't decode keeps its default. Range checks in `init` blocks, such as App Grid columns, take part in this;
  - finally, a document-specific repair runs (`LayoutRules.normalize` for the layout).
- A file that can't be parsed at all, isn't an object, or whose version is newer than the app knows has nothing usable. Then `decodeOrNull` returns `null` and `decode` returns the defaults, without crashing (NFR-REL-03). In every other case, valid data is kept. For the layout, `null` means a first run.
- **Saved names are part of the format.** `GridItem` subclasses and enum constants carry explicit `@SerialName`s. Adding a field with a default needs no migration. Renaming, removing or restructuring one needs a migration.
- **Frozen samples.** `PersistenceTest` keeps one file per released version under `domain/src/test/resources/persist/`, with every field set to a non-default value. Each one must still decode, so a format change without a migration fails the build.

**Implementation notes**

- **App list.** `getActivityList` for every profile, without the launcher's own package. It is queried again after every `LauncherApps.Callback` event, a locale change (names change) and a managed-profile change (FR-GEN-10). A profile that can't be read keeps its last list, or is left out if it was never read: an emptied profile would make the reconciler drop its apps from the layout, and one unreadable profile must not hide the others.
- **App info and uninstall** (FR-GRID-06). `openAppInfo` calls `startAppDetailsActivity`. `requestUninstall` starts `ACTION_DELETE` for the app's package, with `Intent.EXTRA_USER` for its profile, over the visible launcher so Back returns to it. Each app's `AppEntry.removable` is false for system apps (`FLAG_SYSTEM`), which can't be uninstalled, only have their updates removed; the menu then leaves Uninstall out, as the platform's launcher does.
- **Icons.** `icon(app, sizePx)` renders off the main thread into an ARGB bitmap of the requested size and returns its pixels as an `AppIconImage`, so the Domain stays free of platform image types (AR-01).
  - An adaptive icon is drawn full-bleed, from its background and foreground layers and without the device's mask, and marked `shaped`. Presentation clips it to the one icon shape (UI-05). Other icons are drawn as they are, keeping their aspect ratio.
  - Apps of another profile get the system's badge (FR-GEN-10) as a separate full-size layer, made by badging a transparent square, so clipping the icon never clips the badge.
  - `AppEntry.version` counts each package's change events in this process. Presentation's `AppIcons` caches the converted `ImageBitmap`s in an LRU keyed by `AppId`, version and size, so an updated app's icon is loaded again (FR-GEN-06).
- **Launch animation** (FR-ANIM-02). `launch(app, bounds)` passes `ActivityOptions.makeScaleUpAnimation(rootView, …bounds)` to `startMainActivity`, so the app's window grows from the tapped icon or cover. Presentation measures the bounds in the window, which fills the screen.
  - The root view comes from `ForegroundActivity`, a holder that `MainActivity` fills in `onCreate` and clears in `onDestroy`, through `AppGraph.attach` and `detach`, so it never imports `:adapters`. It keeps a weak reference.
  - The same holder supplies the Activity for the default-Home prompt (FR-GEN-02), the Activity context for starting intents and the window token for wallpaper offsets.
- **Default apps** (FR-HOME-07). `defaultApps()` resolves `DIAL`, `SENDTO smsto:`, `VIEW https:` (browsable) and `STILL_IMAGE_CAMERA` with `MATCH_DEFAULT_ONLY`, each on its own. The result counts only if it is a launchable app of the main profile, so the system's resolver, which answers when there are several handlers and no default, is skipped. `LauncherAppsCatalogTest` compares the results with `cmd package resolve-activity`.
- **Links** (FR-EVT-03). `open(SystemScreen.Link)` starts `ACTION_VIEW` with `CATEGORY_BROWSABLE` over the visible launcher, only for `https` links, and does nothing without a browser. *Built in #10;* the system Settings app and the usage access screen arrive with #11 and #19.
- **Notifications** (FR-EVT-04 to FR-EVT-07). *Built in #10.*
  - The system binds `LauncherNotificationListener` once the user grants access. It only reports that it connected or disconnected and *that* something changed (a counter); `ListenerNotificationSource` reads the active notifications and the ranking from it on each change, while the store collects them. Nothing is kept between reads (NFR-PRIV-05).
  - `granted` asks `isNotificationListenerAccessGranted` on every collection and whenever the listener connects or disconnects; a disconnect alone isn't a revocation, because the system also rebinds listeners.
  - Which ones are listed is pure (`NotificationRules`, tested on the JVM): not the launcher's own, not those the system hides (a suspended app, or Do Not Disturb keeping them out of lists), not those with neither a title nor text, and not a group's summary while its notifications are listed. Ongoing ones are listed but can't be dismissed. Newest first.
  - A notification's app is its package and the profile's serial number; the domain finds its catalog entry (`NotificationGroups`). Its name comes from `LauncherApps.getApplicationInfo`, so an app without a launcher activity is still named, or else the package.
  - `open` sends the content intent with the launcher's right to start activities while it is visible (`setPendingIntentBackgroundActivityStartMode`: `ALLOW_IF_VISIBLE` on API 36+, `ALLOWED` on 34–35), growing from the tapped row, and then cancels an auto-cancelling notification as the shade would. Without an intent, it opens the app.
  - `dismiss(refs)` cancels only those that are dismissible and unchanged since they were shown (same post time), so a message that arrives under the same key during the remorse countdown isn't cleared unseen.
  - `requestAccess` opens the listener's own detail screen on API 30+ (`ACTION_NOTIFICATION_LISTENER_DETAIL_SETTINGS`), else the list of listeners. It lives in this port, not in `AppCatalog.open`, because only this adapter knows the listener, which keeps it removable (AR-09).
- **Cropping is done by the launcher** (FR-WP-04). The image is decoded only inside the crop rectangle and handed to the system at the screen's exact aspect ratio, so OEM handling of crop hints doesn't matter (R-5). When the source is wide enough, the crop keeps up to 5% extra width for the parallax of FR-ANIM-14.

### 5.2 Network policy (Bing feed)

| Rule | Implementation | Serves |
|---|---|---|
| Endpoints | The feed is `https://www.bing.com/HPImageArchive.aspx?format=js&idx=0&n={1 or 8}&mkt={market}`. Image URLs are built from `urlbase`. | IF-WP-01, IF-WP-04 |
| HTTPS only, known hosts only | Each URL must be `https` on an allowlisted Bing host (`bing.com`, `bing.net` and their subdomains). | IF-WP-02, NFR-PRIV-01 |
| Redirects | `instanceFollowRedirects = false`. The adapter follows at most 3 redirects itself, and only to URLs that pass the allowlist. | IF-WP-02 |
| Cleartext | Disabled app-wide by `network_security_config.xml` (`cleartextTrafficPermitted="false"`). | IF-WP-02 |

| Size limits | The feed is capped at 256 KB and each image at 5 MB. `Content-Length` is checked first, then a counting stream aborts at the limit. Connect and read timeouts are 15 s each. | IF-WP-05 |

URL building, the allowlist and redirect decision, the counting stream and the JSON parser are pure Kotlin in `adapters/bing/`. They are tested as JVM unit tests against recorded feed samples.

### 5.3 Storage and backup

- **Backed up.** `layout.json` and `settings.json` live in `filesDir` and are included in Auto Backup and device-to-device transfer. `dataExtractionRules` (API 31+) and `fullBackupContent` (API 29–30) both list exactly these two files (SRS §8).
- **Not backed up.** The wallpaper cache and its index live in `noBackupFilesDir/wallpapers/`. The platform never backs that folder up and, unlike `cacheDir`, never clears it. So the pinned and applied images survive low-storage conditions (NFR-REL-02).
- **Atomic writes.** Every write goes through `AtomicFile`: write a temporary file, sync it, then rename. A crash never leaves a half-written file where a good one was (NFR-REL-03). At API 29 `AtomicFile` still uses its older backup-file scheme, so a read during a write would lose that write. `FileStorage` serializes reads and writes behind one lock, and a *first* write cut short can leave a partial file that reads as corrupt.
- **Images** are stored as `noBackupFilesDir/wallpapers/images/<id>.jpg`. IDs are restricted to letters, digits, `_` and `-`, so an ID can never name another path. Turning Daily off deletes the whole `wallpapers/` folder (`clearWallpaperCache`).
- **Checked by tests.** `BackupRulesTest` (JVM, in `:app`) compares both backup XMLs with `FileStorage.BACKED_UP_FILES`. `FileStorageTest` (on a device, in `:adapters`) checks locations, atomic replacement and cache clearing.
- **Nothing exposed to other apps** (NFR-PRIV-06).
  - There is no `ContentProvider`.
  - The only exported components are `MainActivity` (required for the Home role), the notification listener (protected by `BIND_NOTIFICATION_LISTENER_SERVICE`) and the job service (protected by `BIND_JOB_SERVICE`).
  - No intent extra can change the layout, settings or wallpaper choice.

### 5.4 Scheduling

- **The one job** (AR-06). `WallpaperJobService` is the only background job. It is a periodic `JobInfo` with:
  - a 3-hour period;
  - a required network type of *any*, or *unmetered* when "Wi-Fi only" is set;
  - `setPersisted(true)`, so the job survives reboots.
- **Retries** use the same service with a one-off job that has `setMinimumLatency(backoff)`.
- **Data Saver and Battery Saver** are checked by `WallpaperPolicy` when the job runs, because JobScheduler has no constraint for them (FR-WP-06).
- **One code path.** The job and the "Home shown" trigger dispatch the same action, so they share the last-check time and the 8-checks-a-day cap (NFR-PWR-01).
- **Nothing else runs in the background.** There are no wake locks, alarms, foreground services or long-lived connections (NFR-PWR-02).
- **Data use.** About one image a day, typically well under 1 MB, plus small feed requests. That stays inside 40 MB a month (NFR-PWR-03).

### 5.5 Optional features (AR-09)

- `NotificationSource` and `UsageSource` each have a `Disabled` implementation, with empty flows and `granted = false`.
  - The store uses the real adapter only while the setting is on and access is granted: it collects notifications only then (and while the launcher is shown), and sends opening and dismissing to `Disabled` otherwise. *Built in #10 for notifications.*
  - When access is revoked, the store turns the setting off (FR-ONB-04, §4.1).
- App shortcuts (FR-HOME-09, FR-GRID-10) are checked with `hasShortcutHostPermission()` and return an empty list when unavailable.
- Each optional adapter is a separate package that no other adapter references. Deleting it, together with its line in `AppGraph`, leaves a working app.
- Notification contents stay in memory, in the current list only. They are never written, logged or sent anywhere (NFR-PRIV-05, SRS §8).

## 6. Presentation layer

### 6.1 Activity and window

- **One Activity for every surface.** `MainActivity` (a `ComponentActivity` that calls `setContent`) hosts Home, the App Grid, Events, the Top Menu, folders, Settings, Wallpaper details and the tutorial. Settings is a launcher page, not a separate Activity, so it shares the appearance, tokens and transitions (FR-THM-07, UI-01).
- **Window.**
  - The theme sets `windowShowWallpaper=true` and a transparent window background, so the system draws the wallpaper behind the launcher.
  - The window is edge-to-edge with transparent system bars.
  - Status-bar and navigation-bar icons switch between light and dark to suit the surface underneath them (FR-THM-08, FR-HOME-01).
  - The theme's parent has no action bar (UI-03), and the theme sets `soundEffectsEnabled=false`, so no view plays the system click sound (UI-09). `ThemeRulesTest` checks the theme and that the manifest applies it to every activity.
- **Insets.** Content is padded by `WindowInsets.safeDrawing`, which covers cutouts, rounded corners and system bars (UI-07, NFR-COMP-02). Gestures ignore touches that start inside `WindowInsets.systemGestures` (FR-GEST-04, C-5).
- **Home press.** A new intent with `ACTION_MAIN` and `CATEGORY_HOME`, received through `addOnNewIntentListener`, dispatches `Action.HomePressed` (FR-GEN-03). The intent that creates the Activity isn't one. When the launcher returns from another app, Home settles in from 96% scale and partial transparency over the Medium duration (FR-ANIM-03).
- **Back.** One always-enabled `OnBackPressedCallback` dispatches `Action.Back`, which does nothing on bare Home (FR-GEN-04).
  - This works with predictive back. Predictive back is on by default for apps targeting API 36, and `onBackPressed` is no longer called there. So all back handling goes through `OnBackPressedDispatcher`.
- **Shown and hidden.** `onStart` dispatches `Action.HomeShown`, which may offer the default Home role on a first run (FR-GEN-02) and may trigger a wallpaper check (FR-WP-02). `onStop` dispatches `Action.HomeHidden`, which ends the launch guard (FR-GEN-05).

### 6.2 Layers

Drawing order, back to front:

1. System wallpaper
2. Dim and blur
3. Home
4. Events (enters sideways)
5. App Grid (enters from the bottom)
6. Top Menu (enters from the top)
7. Overlays (folder, context menu). The keyboard is the system's own window, over all of them.
8. Remorse banner
9. Tutorial hints

Each way out of Home is a *track* with its own `Animatable<Float>`, owned by the gesture controller: the App Grid's progress from 0 to 1, and the Events carousel (§6.3). The Domain's `LauncherState` says which layer is the target.

### 6.3 Gesture and motion (AR-04)

One `LayerGestureController` in `ui/motion/` drives every view transition. #7 built it for the Home ⇄ App Grid axis, and #10 made it one `Track` per way out of Home and added Events'. The Top Menu (#11) adds a track and its rows in `GestureMath.route`; nothing else changes.

| Behavior | Implementation | Serves |
|---|---|---|
| Recognition | `Modifier.layerGestures` on the root, which never moves, watches each touch in the Initial pass, before the elements under it. A touch that starts outside the system gesture insets, on a resting layer, is taken over once it passes the platform touch slop *before* the long-press timeout, locked to its dominant axis, in a direction the layer owns, as the pure `GestureMath.route` decides. From Home: up opens the App Grid (unless Home's covers can still scroll), down opens the Top Menu (#11), sideways either way opens Events. On Events, sideways either way returns to Home. Until then, taps, scrolling and long-presses reach the elements as usual; a long-pressed item keeps its touch for dragging. Taking over at the root, rather than through nested scrolling, keeps distances and the release velocity in screen coordinates while the surfaces slide. | FR-GRID-01, FR-EVT-01, FR-TOP-01, FR-GEST-04 |
| Tracking | Progress = drag distance ÷ layer travel, 1:1 from recognition. | FR-GEST-01 |
| Release | Complete if progress ≥ 0.30, or if the release velocity toward the target is at least the platform minimum fling velocity. Otherwise return to the start (peek). | FR-GEST-02, AC-05 |
| Settling | `spring(dampingRatio = 1f)`, which is critically damped, seeded with the release velocity. | §4.9 tokens |
| Interruption | Touching during a settle stops the `Animatable` and continues the drag from its current value. | FR-GEST-03 |
| App Grid close | The same take-over: while the grid can't scroll back any further, a downward swipe goes to the controller instead of the list. | FR-GRID-04 |
| Open folder | While a folder is open, resting layers take no swipes, so a downward pull on the panel reaches its pulley menu instead of closing the grid. | FR-FOLD-07 |
| Layer changes from the store | When the store changes the layer, for example on a Home or Back press, the controller animates there. A Home press that brings the launcher back from another app arrives before its window has focus; then it jumps, so the grid isn't seen closing. | FR-GEN-03, FR-GEN-04 |
| Events carousel | A two-page carousel that wraps around, measured in screen widths: Home rests on even numbers and Events on odd ones, and a finger moving left counts up. So the content follows the finger, Events comes in from whichever side it is pushed toward, and either swipe on Events brings Home back. `GestureMath.homeShift` and `eventsShift` place the two pages; Home changes sides only while it is out of view. After a settle the position goes back near 0 by whole turns (`normalize`), which looks the same. A store-driven change, such as Back, sends Events out the way it came in (`carouselRest`); opened without a finger, by the screen reader, it comes in from the end side of the layout direction. *Built in #10.* | FR-EVT-01, FR-GEN-04 |
| Events | Sideways swipes that start on a dismissible notification go to that notification instead. Each one registers its layout coordinates in the controller's `SidewaysClaims`, and the root asks where a touch started before taking a sideways swipe on Events. The bounds are measured when asked, so a scrolled list is never out of date. *Built in #10.* | FR-EVT-05 |
| Dim and blur | The dim follows App Grid progress, or how much of Events is in view, whichever is more; the blur follows the App Grid only. Home slides up out of the way as the grid slides in, as one sheet, and sideways as Events comes in. | FR-ANIM-01 |
| Reduced motion | When the system animator scale is 0 or Animations is set to Reduced, settles and enter/exit animations become snaps or fades of at most 100 ms. Drags still follow the finger. | FR-ANIM-15, NFR-A11Y-05 |

The release decision, direction lock, rubber band and pull-depth mapping are pure functions (`GestureMath`), unit-tested on the JVM. Thresholds, durations, easings and springs are defined once, in `ui/tokens/Motion.kt`.

### 6.5 Design tokens and ambience (UI-08, AR-04)

`ui/tokens/` is the only place that defines colors, sizes, radii, durations, easings and springs. No literal color, dp, sp, radius, alpha or duration appears anywhere else.

- **Colors per appearance** (`Colors.kt`). The highlight itself comes from state; `highlightDefault` is used when there is none (FR-AMB-03).

  | Token | Light | Dark | Use |
  |---|---|---|---|
  | `textPrimary` | `#111111` | `#F5F5F5` | Text and icons at primary emphasis |
  | `textSecondary` | `#3A3A3A` | `#CCCCCC` | Text at secondary emphasis |
  | `glass` | white at 68% | black at 68% | Panels, cards, menus |
  | `scrim` | white at 68% | black at 68% | The strongest scrim behind text drawn straight on the wallpaper |
  | `dim` | white at 68% | black at 68% | The App Grid's backdrop at full progress |
  | `highlightDefault` | `#005A70` | `#6CCFF6` | Headers and states when the wallpaper gives no color |

- **Glass is contrast-tested** (NFR-A11Y-03). Every backdrop alpha is below 1, so the wallpaper always shows through (UI-01), and as low as the contrast targets allow. Secondary text sets that floor. In both appearances, on glass, scrim and dim over both worst-case wallpapers (pure white and pure black):
  - text at both emphasis levels reaches 4.5:1 (worst case: Light 8.4 and 5.1, Dark 7.2 and 4.9);
  - the default highlight reaches 3:1 (worst case: Light 3.5, Dark 4.4). 3:1 is enough because the header and display styles are WCAG large text (at least 24 sp), and the highlight is never used for body text (FR-AMB-04).
  - `DesignTokensTest` (a JVM test) checks all of this with the Domain's `Contrast`, which composites each backdrop over the wallpaper the way Android does.
- **Scrims adapt** (FR-HOME-01, FR-THM-05). Home's clock and cover labels sit on gradient scrims whose strength comes from the brightness of the wallpaper behind them. For launcher-set images, that brightness is computed alongside the highlight color. For other wallpapers, it comes from `WallpaperColors` hints, with the worst case as the fallback. The `scrim` token is that worst case: an adaptive scrim is never stronger.
- **Type** (`Type.kt`). The system sans-serif family (`FontFamily.Default`), in four roles: display 64 sp light (the clock), header 32 sp light, body 18 sp and label 14 sp. There are two emphasis levels, primary and secondary, drawn in `textPrimary` and `textSecondary`. All sizes are in `sp` (UI-04, NFR-A11Y-04). No font is bundled (C-3, NFR-PERF-07).
- **Layout.** `Spacing` is a 4 dp scale: `Step` 4, then 4, 8, 12, 16 (`Gutter`), 24 and 32 dp. `Sizes` holds the one icon size (56 dp, UI-05) and the minimum touch target (48 dp, UI-06). `Radii` and `Shapes` hold the glass corner (12 dp) and the icon shape (16 dp).
- **Motion.** The SRS §4.9 tokens: Short 150 ms, Medium 250 ms, Long 400 ms, Ambient 800 ms; decelerate and accelerate easings; a critically damped spring; rubber-band resistance.
- **`LauncherTheme`** provides the tokens and the current highlight through composition locals. #13 and #17 make it animate every color:
  - appearance changes crossfade over Long without reloading the screen (FR-ANIM-11, FR-THM-03);
  - highlight changes move over Ambient (FR-ANIM-10).

**Enforcement.** `LayerRulesTest` scans `app/src/main` and fails on:
- a literal color, `dp`, `sp`, percent radius, alpha or duration outside `ui/tokens/` (AR-04, UI-08);
- `clickable`, `combinedClickable`, `selectable` or `toggleable` outside `Modifier.pressable` (UI-06);
- `BasicText` outside `ui/components/`, or `FontFamily`, `FontWeight` or `TextStyle` outside `ui/tokens/` (UI-04);
- any audio API (`SoundPool`, `MediaPlayer`, `AudioManager`, `ToneGenerator`, `playSoundEffect`, …), also in `:adapters` (UI-09).

### 6.6 Wallpaper display

- **Normally the system draws the wallpaper**, and the launcher never draws its own copy.
- **Crossfade** (FR-ANIM-10). When a new image is applied while Home is visible:
  1. Presentation covers the screen with the outgoing image, taken from the cache at the same crop.
  2. The adapter applies the new system wallpaper underneath.
  3. The overlay fades out over Ambient (800 ms).
  - If the outgoing wallpaper wasn't set by the launcher, it isn't cached, and the change is instant.
- **Blur and dim** (FR-GRID-01, NFR-COMP-03).
  - On API 31+, while cross-window blur is available, the window's background blur radius (`Window.setBackgroundBlurRadius`) follows App Grid progress, up to 32 dp (`ui/motion/WindowBlur`). Availability is checked with `WindowManager.isCrossWindowBlurEnabled` and observed with `addCrossWindowBlurEnabledListener`.
  - Otherwise the dim alone shows. That covers API 29–30, Battery Saver and devices without blur support. #26 makes it stronger there (NFR-COMP-03).
  - See R-1.
- **Parallax** (FR-ANIM-14, C). Moving between Home and Events sets wallpaper offsets through `SystemWallpaper`.

| Level | Where | Runs on | When |

### 8.2 How a requirement is traced

- **Tests declare what they verify.** Every test that verifies a requirement carries `@Verifies("FR-SRCH-02", …)`. The annotation lives in `:domain` test fixtures and is shared by all test source sets. An annotation is used instead of the test name because method names containing spaces are not allowed in on-device tests at minSdk 29.
- **Review items declare it too.** Each item in `REVIEW-CHECKLIST.md` starts with the IDs it covers, for example `- [ ] [C-3, UI-09] No Jolla or Microsoft assets; no sounds.`
- **`./gradlew checkTraceability`** is part of `check` and so runs on every PR. It:
  1. collects every SRS ID whose priority is M or S, plus every `AR-` and `AC-` ID;
  2. collects the IDs in all `@Verifies` annotations and in `REVIEW-CHECKLIST.md`;
  3. fails, listing each one, if an ID has no test or checklist item, or if an ID that doesn't exist in the SRS is referenced (a typo, or a removed requirement).
  - C-priority IDs are reported but don't fail the build.
  - When the SRS changes, the build fails until the tests or checklist catch up.
- **Other build checks:**
  - `checkDependencies` compares the release runtime classpath of `:app` with `gradle/runtime-dependencies.txt`, an allowlist that mirrors §7.1, and fails on any addition or removal (AR-08, NFR-PRIV-02, NFR-PRIV-07).
  - `checkPermissions` compares the merged manifest's permissions with §5.6 (NFR-PRIV-04).
  - `checkApkSize` fails if the release APK is 10 MB or larger (NFR-PERF-07).
  - Android Lint runs with warnings treated as errors.

## 9. Risks and spikes

| ID | Risk | Mitigation |
|---|---|---|
| R-1 | Window blur-behind may need a translucent window, and changing its radius on every frame may drop frames (NFR-PERF-02). The official blur guide could not be checked while writing this design. | A spike in the first UI milestone, measured with `FrameTimingBenchmark`. If it falls short, set the blur only at rest (closed or open) and animate only the dim. Dim-only is already the fallback (NFR-COMP-03). **Spike (#7):** the blur follows progress through `Window.setBackgroundBlurRadius`, with the window left opaque. On the Galaxy S22 (One UI, Android 16) the platform reports cross-window blur as disabled, so the grid shows the dim alone there, and the blur path is still unchecked on hardware. Still open: check it on a device that supports cross-window blur, such as a Pixel, with `FrameTimingBenchmark` (#20). |
| R-2 | FR-TOP-07 (Could) can only open the notification shade through a non-SDK interface (`StatusBarManager.expandNotificationsPanel` with `EXPAND_STATUS_BAR`), which future Android versions may block. | Ship the setting only if it works on the target API level. Otherwise hide it. No M or S requirement depends on it. |
| R-3 | The Bing feed is undocumented, and its terms of use are unclear (Q-3, A-1). | All Bing knowledge is confined to `adapters/bing`. The launcher keeps working from its cache (FR-WP-11). If legal review requires, the feature can ship turned off. |
| R-4 | The Android documentation doesn't say whether `LauncherApps.getActivityList` is filtered by package visibility for apps without `QUERY_ALL_PACKAGES`. | `LauncherAppsCatalogTest` (#5), run on an API 30+ device, compares the result, with only the `<queries>` block of §5.6, against `cmd package query-activities` for `MAIN`/`LAUNCHER`. If apps are missing, add `QUERY_ALL_PACKAGES`, justify it (a launcher must see all launchable apps) and update §5.6 and `checkPermissions`. **Result (#5):** passed on API 36 (Galaxy S22, Android 16): every launchable app is listed, so `QUERY_ALL_PACKAGES` isn't needed. |
| R-5 | OEMs handle wallpapers differently: some ignore crop hints, some zoom, and some recolor system UI from the wallpaper (A-4). | The launcher crops the image itself (§5.1), so crop hints are never relied on. Test on at least two OEM devices besides the reference device. |
| R-6 | Compose and its dependencies could push the APK toward the 10 MB budget (NFR-PERF-07). | `checkApkSize` runs from the first scaffold onward. Material is excluded, and R8 full mode is on (TD-05). |
